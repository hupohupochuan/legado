## 优先级 B：数据库 LIKE 查询优化（中风险、中等收益）

### B1. 书架搜索引入 FTS4 全文索引

**现状**: `data/dao/BookDao.kt:106-110` 的 `searchShelfBooks` 用 `LIKE '%key%'` 前导通配符，全表扫描。书架书籍多时搜索卡顿。
```
WHERE name LIKE '%' || :key || '%' COLLATE NOCASE
OR author LIKE '%' || :key || '%' COLLATE NOCASE
OR originName LIKE '%' || :key || '%' COLLATE NOCASE
...
```
**风险**: 中（需数据库 Migration，改不好会丢用户数据）
**工作量**: 中（3-5 小时含 Migration 测试）
**前置**: 必须先读 `data/AppDatabase.kt` 的 Migration 机制
**做法**:
1. 读 `data/entities/Book.kt`，确认当前表结构。
2. 读 `data/AppDatabase.kt` 的版本号和 Migration 列表。
3. 新增 FTS4 虚拟表 `books_fts` 映射 name/author/originName/kind/intro。
4. 用触发器同步 books 表和 books_fts 表（INSERT/UPDATE/DELETE）。
5. 新增 DAO 方法 `searchShelfBooksFts(key)` 用 `MATCH` 查询。
6. 写 Migration（版本号 +1），在 `MigrationTest`（androidTest）里验证。
7. `BookshelfViewModel`/搜索入口改用新 DAO 方法。
**关键陷阱**:
- FTS4 的 `MATCH` 是分词匹配，中文需配合 `sqlite3_fts5` 或 ICU 分词器，否则中文搜索效果差。**务必先验证 Android SQLite 是否支持中文分词**，不行则改用 `LIKE` 但加 `LIMIT` + 索引优化。
- Migration 必须在 androidTest 里覆盖，否则升级时崩。
**验证**:
- `./gradlew :app:assembleDebug --no-daemon`（编译）
- `./gradlew :app:connectedDebugAndroidTest --tests "*MigrationTest*" --no-daemon`（Migration）
- 手动：书架 500+ 本书时搜索响应时间对比
**文件**: `data/entities/`、`data/dao/BookDao.kt`、`data/AppDatabase.kt`、`androidTest/.../MigrationTest.kt`

### B2. 章节标题搜索（可选，优先级低）

**现状**: `BookChapterDao.kt:13,16` 的 `LIKE '%key%'` 搜索章节标题。通常单书章节数不大（<3000），全表扫描影响有限。

## 优先级 C：CI/CD 补全（低风险、高长期价值）

### C1. 给现有 test.yml 补单元测试和编译检查步骤

**现状**: `.github/workflows/test.yml` 存在但只做 `assembleRelease` + 发布，**不跑单元测试、不跑 check-debug.sh、不跑 lint**。PR 合入前无自动化质量门禁。
**风险**: 低（只加 CI 步骤，不改业务代码）
**工作量**: 小（1-2 小时）
**前置**: 无
**做法**:
1. 在 `test.yml` 的 `build` job 前加一个 `check` job：
```yaml
  check:
    needs: prepare
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: 17
      - uses: gradle/actions/setup-gradle@v4
      - name: Compile check
        run: ./gradlew :app:compileAppDebugKotlin --no-daemon
      - name: Unit tests
        run: ./gradlew :app:testAppDebugUnitTest --no-daemon
      - name: Lint
        run: ./gradlew :app:lintAppDebug --no-daemon
        continue-on-error: true  # 初期先警告不阻断
```
2. 让 `build` job `needs: [prepare, check]`，编译/测试失败则不构建。
3. **注意**: 项目用 JDK 17（见现有 test.yml:62），Gradle 9.4.1 需 JDK 17+。
**关键陷阱**:
- `lintAppDebug` 可能有很多历史 warning，第一次跑用 `continue-on-error: true` 不阻断，后续逐步收紧。
- 单元测试若依赖 Android Framework（appCtx）会失败，只跑纯 JVM 测试（model/、help/book/ 下的）。
**验证**: push 到 master 观察 CI 是否跑通；故意改坏一个测试看是否拦截。
**文件**: `.github/workflows/test.yml`

### C2. 接入 Detekt 静态分析（可选）

**现状**: 无静态代码分析工具。
**风险**: 低
**工作量**: 小（1-2 小时配置 + 持续处理告警）
**前置**: C1 完成
**做法**:
1. 在 `gradle/libs.versions.toml` 加 detekt 依赖。
2. 根 `build.gradle` 加 detekt 插件。
3. `app/build.gradle` 应用插件并配置 `detekt { ... }`。
4. 新建 `config/detekt/detekt.yml`，先宽松配置（只禁用明显不合理的规则）。
5. CI 里加 `./gradlew detekt --no-daemon`，初期 `continue-on-error: true`。
**关键陷阱**:
- detekt 首次跑会有几百条告警，不要一次性全修，先 baseline：`./gradlew detektBaseline`。
- 不要启用 `MagicNumber`、`WildcardImport` 等历史项目不适合的规则。
**验证**: `./gradlew detekt --no-daemon` 本地跑通。
**文件**: `gradle/libs.versions.toml`、`build.gradle`、`app/build.gradle`、`config/detekt/detekt.yml`

## 优先级 D：上帝类拆分（高风险、需分阶段）

### D1. AppConfig 按领域拆分

**现状**: `help/config/AppConfig.kt` 766行，混合阅读/漫画/书架/导出/点击区域 5 类配置，被 **154 个文件**引用。
**风险**: 高（154 文件需改 import 和调用点，漏改会编译失败或运行时 NPE）
**工作量**: 大（8-16 小时，强烈建议分多次）
**前置**: 建议先完成 A1-A3 测试，有测试兜底再动
**做法**:
1. **不要一次性拆**。先按域统计引用：`grep -rl "AppConfig\.manga" app/src/main/java`（manga 4 文件）、`AppConfig\.export`（4 文件）、`AppConfig\.bookshelf`（6 文件）、`AppConfig\.clickAction`（2 文件）。
2. **先拆引用最少的域**：`ClickActionConfig`（2 文件引用）风险最低。
3. 拆法：
   - 新建 `help/config/ClickActionConfig.kt`（object），把 clickActionTL/TC/TR/ML/MC/MR/BL/BC/BR 9 个字段和 PreferKey 监听移过去。
   - 原 `AppConfig` 保留同名 `val clickActionTL by ClickActionConfig` 委托属性，**保持 154 文件不改**。
   - 后续逐步迁移引用方从 `AppConfig.clickActionTL` 改为 `ClickActionConfig.clickActionTL`。
4. 每拆一个域：编译 + 全量测试 + commit 一次。
**关键陷阱**:
- `AppConfig` 实现了 `SharedPreferences.OnSharedPreferenceChangeListener`，在 `App.kt:67` 注册。拆分后监听器要跟着拆，否则配置变更不生效。
- 用委托属性过渡比直接改 154 文件安全得多，**务必用委托模式**。
**验证**: 每拆一个域跑 `scripts/check-debug.sh` + `testAppDebugUnitTest`。
**文件**: `help/config/AppConfig.kt`、新建 `help/config/ClickActionConfig.kt`/`MangaAppConfig.kt`/`BookshelfAppConfig.kt`/`ExportAppConfig.kt`

### D2. ReadBook 继续拆分 ContentDownloader

**现状**: `model/ReadBook.kt` 1042行。本轮已拆出 `ContentDownloadState`（状态字段），但下载调度逻辑（`download`/`downloadIndex`/`downloadAwait`/`preDownload`/`cancelPreDownloadTask`）仍在 ReadBook。
**风险**: 中（`CacheBook` 直接访问 `ReadBook.downloadedChapters`，拆动需改 CacheBook）
**工作量**: 中（3-5 小时）
**前置**: 本轮已完成 ContentDownloadState 抽取
**做法**:
1. 新建 `model/ContentDownloader.kt`，把 `download`/`downloadIndex`/`downloadAwait`/`preDownload` 移入。
2. 通过构造参数注入：`book: () -> Book?`、`bookSource: () -> BookSource?`、`chapterStore`、`chapterLoadState`、`downloadState`、`contentLoadFinish` 回调。
3. `CacheBook.Download` 里 6 处 `ReadBook.downloadedChapters.add/remove` 改为通过 `downloadState.markDownloaded/markFailed`（CacheBook 需持有 downloader 引用或通过回调）。
4. **注意**: `preDownload()` 依赖 `durChapterIndex`/`chapterSize`/`AppConfig.preDownloadNum`，这些是 ReadBook 状态，需作为参数传入或用 lambda。
**关键陷阱**:
- `contentLoadFinish` 是 ReadBook 的核心方法（处理排版分页、callBack 回调），downloader 回调它时需确保线程安全。
- `ReadMangaViewModel` 也有自己的 `preDownload`/`download`，逻辑差异大，不要强行合并调度逻辑（本轮已验证差异）。
**验证**: `scripts/check-debug.sh` + `ContentDownloadStateTest` + 手动测试预下载/切章/朗读。
**文件**: `model/ReadBook.kt`、新建 `model/ContentDownloader.kt`、`model/CacheBook.kt`

### D3. ReadBookActivity 进一步拆分（不建议做）

**现状**: 1805行，但已有 4 个内部类委托（`ReadBookKeyHandler` 141行、`ReadBookMenuHandler` 245行、`ReadBookEventHandler` 109行、`ReadBookColorHandler` 61行），主 Activity 体约 1230 行。
**评估**: **不建议做**。剩余 1230 行是 UI 生命周期 + 绑定初始化 + 业务编排，规模可接受。进一步拆分需把内部类变顶级类 + 注入 binding/viewModel，破坏直接访问便利性，回归风险高于收益。除非有明确的新功能开发受阻于 Activity 体积，否则不动。

## 优先级 E：其他低优先级

### E1. `!!` 强解包继续清理

**现状**: 全项目约 127 个 .kt 文件含 `!!`。本轮只清理了 ReadBook 的 2 处。
**风险**: 低（逐个改为 `firstOrNull`/`getOrNull`/`?: return`）
**工作量**: 持续（建议每次顺手改，不单独安排）
**做法**: 改任何文件时若看到 `!!`，评估是否可用安全替代。**不要专门扫一遍全改**——有些 `!!` 在私有函数内有前置非空保证是安全的，盲目改会冗余。

### E2. modules/book 模块化落实

**现状**: `modules/book` 近乎空壳（仅注解依赖），书源解析/ContentProcessor 仍在 app。
**评估**: **不建议近期做**。迁移涉及大量 import 改动和模块依赖调整，收益是"结构更清晰"，不解决实际性能或可维护性问题。等有测试覆盖后再评估。

### E3. FlowBus 类型安全改造

**现状**: `utils/FlowBus.kt` 用 `String tag + Any` 事件，42 个事件编译期无类型保证。
**风险**: 中（42 个事件需逐个迁移）
**工作量**: 大（建议分多次）
**做法**: 状态型事件（AUDIO_PROGRESS/AUDIO_STATE）改 `StateFlow`；一次性事件用 `sealed class BusEvent`。**建议等有测试兜底后再做**。
